**スキル**は「タスクのやり方」を再利用できる形にした指示のまとまりで、**ルーティン**は「いつ実行するか」を Bot に教えるものです。スキルで手順を固め、ルーティンで自動化する、という順番で考えると整理しやすくなります。

## スキル

スキルはすべての Bot で共有されます（ただし Bot によっては関連するアプリやログインが必要です）。

### 作り方

いちばん簡単なのは、Bot がいま終えた作業を「名前をつけてスキルとして保存して」と頼むことです。そのとき、次の内容を含めると精度が上がります。

- 参照するシステム
- リスクの定義
- 出力の形式
- 承認のルール

### 実演して教える

**Teach a task** が使える場合は、1 対 1 のチャットで Bot のコンピュータービューを開き、目的を説明してから作業を 1 回やって見せます。記録は画面上の操作が最大 10 分までで、マイク音声は記録されません。できた下書きは安全な例で試し、判断ルールや失敗時の扱い、承認の境界は自分で書き足しましょう。

### 使う

スキルは名前で呼び出します。`@` で Bot、グループ、ルーティン、アプリを参照できます。

## ルーティン

ルーティンは、1 つの Bot に「いつワークフローを動かすか」を伝えます。クラウドで動くので、ノート PC を閉じていても実行されます。

作るときは、その Bot に頼んだうえで、次の点を確認します。

- スケジュールとタイムゾーン
- 入力の情報源
- 期待する結果
- 承認の境界
- 情報源が見つからないときにどうするか

スケジュールは自然な言葉で伝え、**When to run** で保存された内容を確かめます。新しいルーティンは作成時には動かず、次の予定時刻を待ちます。すぐ試すには **Test** を使います（実際に動作し、使用量も消費します）。

## トリガー

スケジュールの代わりに、次のイベントで起動することもできます。

- Slack のメッセージ（メンション、特定のフレーズ、リアクション、任意のメッセージ）
- GitHub / Linear / Sentry / PagerDuty のイベント
- Bot 専用アドレスへのメール
- Webhook（キーを Bearer ヘッダーにつけて HTTP POST。`200` は「開始した」の意味で、完了ではありません）

トリガーを作る前の出来事では起動しません。条件は狭く保つこと。広すぎるトリガーはノイズになり、使用量も無駄にします。

## 上限

| 項目 | 上限 |
|---|---|
| 1 つの Bot が持てるルーティン | 50 |
| ルーティンごとに残る実行記録 | 直近 20 件 |
| スケジュールの最短間隔 | 5 分 |
| 1 時間あたりの実行回数（全ルーティン合計） | 300 |
| 1 時間あたりの実行回数（ルーティンごと） | 200 |

上限を超えた実行は `Automation run rate limit exceeded` で失敗します。週の使用量が足りなくなったら、ルーティンを一時停止するか、条件を絞りましょう。
